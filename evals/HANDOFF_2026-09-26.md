## Binding rules and user preferences

- **Long runs:** ask before any run over 1 hour, with a time estimate. Use at most 2 concurrent Memory Bank writers. Report
  actual spend.
- **Keep it simple:** the user rejected an over-engineered grader. Use one judge call per answer, and add machinery only
  when a concrete failure demands it.
- **Models:** judge gemini-2.5-pro (the strongest available); synthesizer / answer model gemini-2.5-flash. The project
  cannot call Gemini 3.x, and Memory Bank rejects 2.5 as its generation model, so engines run the service default.
- **Probes:** write them in a real customer's voice. Never "what is my email / which number will you call". Do not
  require personal details (phone digits, emails) to be recited; confirming the change is enough.
- **Hand-check the judge:** it makes mistakes in both directions (see the impact and LongMemEval sections).
- **Engines:** do not write eval data into the eval-scratch, consol-flash (frozen rev 3), consol-pro or longmsg engines.
  Do not touch `jpmc-ccb-fraud-memory` (a colleague's). Make no `backend/` changes.

## 2. Attribution audit ("does memory record who said what")

Motivation: the app's architecture pitches a pre-write veracity layer; the long-messages pilot had merged a spouse's
card into the customer's profile.

- **Script:** `audit_attribution.py`, offline. It makes one gemini-2.5-pro call per extract/both scope over the full
  source and labels every memory:
  - STORED_MISSTATEMENT (a person said it wrongly and it was stored as fact)
  - OTHER_PERSON
  - HYPOTHETICAL_AS_FACT
  - WRONG_SPEAKER
  - MEMORY_ERROR
- **Report:** `results/attribution_audit_20260925T184617Z.md`, with a hand review and a correction at the end. The earlier
  `attribution_audit_2026092[5]T16*` files are prompt iterations; ignore them.
- **Result, all 5 customers, hand-verified:** extract 13/274 memories and both 10/89 have a confirmed error, about 2-3 per
  customer.
  - Most common: the customer's mistaken recollection stored as fact ("hotel charge", "resolved" when only the
    provisional credit had posted, blaming the agent for her own typo).
  - Memory Bank's own errors: an old dispute moved to the replacement card (028, 033); a cancelled trip stored as taken
    (033 both); two callbacks merged (016).
  - No third-party misattribution, no hypotheticals stored as facts, no swapped speakers.

## 4. Google docs: can configuration prevent claims being stored as facts?

There is no documented setting for claimed-vs-verified, no extraction-prompt override, and no source or confidence field
on a memory. The levers:
- custom topic descriptions and few-shot examples (these feed the extraction prompt; steering only);
- your own extraction via `direct_memories_source` (at most 5 facts per request, still consolidated) or `create`, which
  allows checking against the records of truth before writing;
- revision labels plus rollback (Google's governance notebook);
- for consolidation errors: metadata with `REQUIRE_EXACT_MATCH` (per card or case), `revisions_per_candidate_count`, or
  consolidation off.

## 5. Literature survey (summary kept in memory `memory-benchmark-literature.md`)

- **Standard benchmarks:** LoCoMo, LongMemEval, MemoryAgentBench, BEAM. Closest to our findings: HaluMem (false-memory
  resistance, update hallucination), MemTrace, STALE, MemSyco-Bench, GroupMemBench (speaker attribution).
- **Gaps:** none covers claims vs system of record, customer service, or multi-channel transcripts.
- **Google publishes no product benchmark.** Its claim rests on the RMM paper (arXiv 2503.08026, 70.4% LongMemEval,
  research prototype).
- **Only public product number:** Redis, 2026-09-21, 42.4% on LongMemEval-S (competitor, GPT-4o answer and judge).
